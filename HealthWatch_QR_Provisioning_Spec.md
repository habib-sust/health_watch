# HealthWatch — QR Code Provisioning Specification

## 1. Problem Statement

The current provisioning flow relies on **WCSession** (Watch Connectivity) to relay a 4-digit code between the paired iPhone and Apple Watch. This has several limitations:

| Limitation | Impact |
|---|---|
| **Paired device required** | Only the iPhone paired with the Watch can provision it. A clinic iPad or another staff iPhone cannot be used. |
| **WCSession reliability** | WCSession messages can be delayed or fail silently when Bluetooth is unstable. The "Watch not reachable" error is common. |
| **Manual code entry on watch** | Entering a 4-digit code on a tiny watch screen is slow and error-prone, especially for elderly patients or those with motor difficulties. |
| **Tight time coupling** | The 120-second code expiry requires both devices to be active simultaneously. |

## 2. New Flow Overview

The redesigned flow uses a **QR code** generated by the Watch and scanned by the iOS app. The Watch and iPhone communicate exclusively through the **server** — no WCSession is needed for provisioning.

### High-Level Flow

```
1. Watch App (unprovisioned)
   └── User taps "Provision" button
   └── Watch generates QR code containing its device ID
   └── QR code displayed on watch screen

2. iOS App
   └── User selects an individual to provision
   └── App opens camera to scan the QR code on the watch
   └── App reads device ID from QR code
   └── App sends POST to server: map individual ↔ device ID
   └── Server creates provisioning record, generates auth token

3. Watch App (polling)
   └── After showing QR code, watch begins polling server every 5 seconds
   └── GET /api/v1/device/{deviceId}/config
   └── Server returns 404 (not yet provisioned) → keep polling
   └── Server returns 200 with config → provisioning complete!

4. Watch App (provisioned)
   └── Stores serverURL, individualId, authToken in Keychain
   └── Transitions to provisioned state
   └── Starts HealthKit collection
```

## 3. QR Code Payload

The QR code contains a **JSON string** with the device ID and a server URL hint:

```json
{
  "deviceId": "A1B2C3D4-E5F6-7890-ABCD-EF1234567890",
  "app": "healthwatch",
  "version": 1
}
```

| Field | Type | Description |
|---|---|---|
| `deviceId` | String (UUID) | Unique identifier for this Apple Watch, from `WKInterfaceDevice.current().identifierForVendor` |
| `app` | String | App identifier, used to validate this is a HealthWatch QR code (not a random QR) |
| `version` | Int | Payload version for future compatibility |

**QR code size:** The JSON payload is ~100 characters. At error correction level M, this fits comfortably in a Version 5 QR code (37x37 modules), which renders clearly even on a 40mm Apple Watch screen.

### Device ID Generation

```swift
// On watchOS
let deviceId = WKInterfaceDevice.current().identifierForVendor?.uuidString ?? UUID().uuidString
```

`identifierForVendor` is stable per app-vendor pair on the device. If the app is reinstalled, it may change — this is acceptable because re-provisioning would be needed anyway.

## 4. API Endpoints

### 4a. Register Device (iOS → Server)

```
POST /api/v1/device/register
Authorization: Bearer <staff-api-token>
Content-Type: application/json

{
  "deviceId": "A1B2C3D4-E5F6-7890-ABCD-EF1234567890",
  "individualId": "individual-001"
}
```

**Response (200):**
```json
{
  "success": true,
  "deviceId": "A1B2C3D4-E5F6-7890-ABCD-EF1234567890",
  "individualId": "individual-001"
}
```

**Response (409 — device already provisioned):**
```json
{
  "error": "device_already_provisioned",
  "currentIndividualId": "individual-002",
  "message": "This device is already provisioned for another individual. Remove the existing provisioning first."
}
```

### 4b. Poll Device Config (Watch → Server)

```
GET /api/v1/device/{deviceId}/config
```

No authorization header needed — the device ID itself is the lookup key. The response contains the auth token the Watch will use for all future authenticated requests.

**Response (200 — provisioned):**
```json
{
  "status": "provisioned",
  "serverURL": "https://api.healthwatch.example",
  "individualId": "individual-001",
  "individualName": "Alice Johnson",
  "authToken": "eyJhbGciOiJIUzI1NiIs..."
}
```

**Response (404 — not yet provisioned):**
```json
{
  "status": "pending"
}
```

### 4c. Remove Device Registration (iOS → Server)

```
DELETE /api/v1/device/{deviceId}
Authorization: Bearer <staff-api-token>
```

**Response (200):**
```json
{
  "success": true
}
```

This endpoint is called when removing provisioning from the iOS app. The Watch's next poll will receive a 404, and it should transition back to unprovisioned.

## 5. Security Considerations

| Concern | Mitigation |
|---|---|
| **QR code interception** | The QR code only contains the device ID, not any secrets. An attacker scanning the QR cannot do anything without also having staff API credentials to call the registration endpoint. |
| **Polling without auth** | The config poll endpoint is unauthenticated by design (the watch has no token yet). The device ID is a UUID (128-bit random), making brute-force infeasible. The response only contains the auth token once — after first retrieval, the server can mark it as delivered. |
| **Token in config response** | The auth token is transmitted over HTTPS. The Watch stores it in Keychain with `kSecAttrAccessibleAfterFirstUnlock`. |
| **Device ID stability** | `identifierForVendor` can change on app reinstall. This is acceptable — a new QR code with the new ID would be generated. |
| **Replay attacks** | The server should invalidate the provisioning record after the config is successfully delivered (first 200 response to the poll). Subsequent polls return 404. |
| **Staff authorization** | The registration endpoint requires a valid staff Bearer token, ensuring only authorized clinicians can map devices to individuals. |

## 6. Comparison with Old Flow

| Aspect | Old (4-Digit Code + WCSession) | New (QR Code + Server Polling) |
|---|---|---|
| **Device pairing** | Requires paired iPhone | Any iPhone with the app |
| **User interaction** | Type 4 digits on watch | Tap "Provision" on watch, scan QR on phone |
| **Network dependency** | Bluetooth (WCSession) | WiFi/cellular (HTTPS) |
| **Time pressure** | 120-second code expiry | No expiry on QR code; polling has configurable timeout |
| **Error handling** | WCSession failures, code mismatch | Standard HTTP errors, clear polling states |
| **Offline capability** | Works without internet (local BT) | Requires internet on both devices |
| **Security model** | Shared secret (4-digit code) | Device ID (UUID) + server-side authorization |
| **Provisioning from iPad** | Not possible (no WCSession) | Possible (just needs camera + API access) |

## 8. Edge Cases & Error Handling

| Scenario | Behavior |
|---|---|
| **Watch loses internet while polling** | Polling pauses, retries with exponential backoff. QR code stays on screen. |
| **User cancels on watch** | Polling stops, returns to unprovisioned state. No server-side cleanup needed (nothing was registered). |
| **iOS app fails to register** | Error shown on iOS. Watch keeps polling, will eventually time out (configurable, default 5 minutes). |
| **QR code scanned by wrong app** | The `"app": "healthwatch"` field allows the iOS app to validate the QR payload. Invalid QR shows an error. |
| **Device already provisioned on server** | Server returns 409. iOS shows error with option to override (re-register). |
| **Watch app killed while polling** | On next launch, if no Keychain config exists, returns to unprovisioned. User can re-initiate. |
| **Multiple watches provisioned for same individual** | Allowed — server maps multiple device IDs to one individual. |
| **Same watch re-provisioned for different individual** | Old mapping is replaced on the server. Watch gets new config on next poll. |
| **Polling timeout** | After 5 minutes of unsuccessful polling, watch shows a timeout message with option to retry. |

## 9. Deprovision Flow

Deprovisioning remains available from the iOS app:

1. iOS app sends `DELETE /api/v1/device/{deviceId}` to the server
2. Server removes the device mapping
3. iOS app clears local `provisionedIndividualId` from UserDefaults
4. Watch's next background heartbeat or data push gets HTTP 401
5. Watch detects token revoked, transitions to `.error(.tokenRevoked)`
6. User taps "Re-provision" on watch → returns to unprovisioned state with QR button

**Alternative (immediate):** If WCSession is available (paired device), iOS can also send a `.deprovision` message over WCSession for instant feedback. This is optional and complementary.
